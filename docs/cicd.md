# CI/CD — push to deploy

**The loop:** tell Claude what to change → Claude commits and pushes → GitHub
Actions tests it and deploys it. Nobody types a command. Day-to-day server
operations (settings, restart/update, Discord setup) are buttons on the
portal's **Admin** page, not scripts.

```
 you ──"change X"──▶ Claude ──git push──▶ GitHub Actions ─┬─ test          2 parallel jobs, pytest -n auto ──┐
                                                         ├─ portal-image  docker buildx → Artifact Registry ─┼─▶ portal  Cloud Run deploy,
                                                         │                (runs WHILE the tests run)         │   smoke test (rollback on failure)
                                                         ├─ infra         terraform apply (after test)  ◀────┘
                                                         └─ changes ─▶ mentat-test ─▶ mentat   (only if Mentat's inputs changed)
```

Workflow: [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml); the test suites are written once in
[`run-tests.yml`](../.github/workflows/run-tests.yml), which `deploy.yml` and `test.yml` (pull requests) both call.
Runs on pushes to `main`, or by hand from the Actions tab ("Run workflow", which always does everything).

## Why this shape

- **No key anywhere.** GitHub Actions authenticates to GCP with Workload
  Identity Federation: GitHub issues a signed OIDC token for this repo's
  workflow run, and GCP exchanges it for short-lived credentials as
  `skippy-deployer`. The provider only accepts tokens from
  `aaronsrhodes2/skippy-tel`. (This also sidesteps the org policy that
  blocks service-account key creation.)
- **Claude never holds cloud credentials.** It edits code and pushes; the
  pipeline does the deploying. That's the part the Claude Code sandbox
  refused to do directly — and it shouldn't have to.
- **Secrets stay in Secret Manager.** The portal reads them at runtime
  (`--set-secrets`); they're never in the repo, the image, or GitHub.
- **Terraform state lives in GCS** (`gs://skippy-tel-tfstate`), so CI and a
  human in Cloud Shell see the same state.

## One-time bootstrap (Cloud Shell, ~10 minutes)

```bash
cd ~/skippy-tel && git pull && bash infra/bootstrap/bootstrap.sh
```

It:
1. installs terraform if Cloud Shell forgot it,
2. applies [`infra/bootstrap/`](../infra/bootstrap): APIs, state bucket,
   Artifact Registry repo, the `skippy-deployer` service account and its
   roles, the Workload Identity pool/provider, and Secret Manager secrets
   (with a generated Flask session key),
3. walks you through creating the "Sign in with Google" OAuth client and
   asks for its ID/secret, plus the optional Anthropic API key (Skippy chat)
   and Discord bot token (Discord setup button). Input is visible and
   format-checked; to re-enter one later: `bash infra/bootstrap/secrets.sh google`
   (or `anthropic` / `discord`), then ask Claude to redeploy,
4. moves the game-server Terraform state from Cloud Shell into the bucket,
5. writes the project number into the workflow and pushes — **that push is
   the first deploy.**

If step 5's push fails, just tell Claude the project number it printed.

### Secrets

| Secret | Used for | Set by |
|---|---|---|
| `portal-flask-secret` | signing portal sessions | generated by bootstrap |
| `portal-google-client-id` / `-secret` | Google sign-in | bootstrap asks |
| `anthropic-api-key` | Skippy chat | bootstrap asks (optional; your vault has it) |
| `discord-bot-token` | Admin → Discord setup | bootstrap asks (optional) |

To change one later (e.g. add the Discord token): Cloud Console → Security →
Secret Manager → the secret → **New version**, then ask Claude to redeploy
(or re-run the workflow from the Actions tab).

**Discord bot token:** <https://discord.com/developers/applications> → New
Application → Bot → Reset Token. Invite it with
`https://discord.com/oauth2/authorize?client_id=<APP_ID>&scope=bot&permissions=536947728`
(Manage Channels, Manage Webhooks, Manage Messages, View Channels, Send
Messages, Read History).

## What each push does

| Job | Does | Needs | Runs when |
|---|---|---|---|
| `test` | calls `run-tests.yml`: job `suite` (portal, memory, tools, home-reporter, claude-bridge, mentat tests) and job `flask-api` (its own requirements), both `pytest -n auto --dist loadfile` | nothing | always |
| `gate` | skips deploys until bootstrap has run | nothing | always |
| `portal-image` | builds `portal/Dockerfile` with buildx (GitHub layer cache), pushes `portal:<sha>` with `GIT_SHA` / `BUILD_TIME` baked in. **Runs while the tests run**: an image that then fails the tests is harmless, nothing deploys it | `gate` | gate ready |
| `portal` | notes the serving revision, deploys `skippy-portal` to Cloud Run, sends traffic to it, smoke-tests it (`/health`, not `/healthz`: Cloud Run reserves paths ending in z; also that Experiments' bundles and Star Control Zero, `/starcontrol/version`, shipped in the image); on failure puts traffic back | `test`, `portal-image`, `gate` | gate ready and tests green |
| `infra` | `terraform apply` in `infra/gcp-games`: VM shape, firewall, the compose file + VM scripts as instance metadata (applied at the VM's next boot) | `test`, `gate` | gate ready and tests green |
| `changes` | decides whether Mentat needs work: `tools/ci_changes.py` compares the tree with the **last successful deploy**, not the push's `before` (a cancelled or red run deploys nothing, so `before` would lose its Mentat change). Any doubt answers "yes" | nothing | always |
| `mentat-test` | Mentat's tests against the pinned sigma-ground | `changes` | Mentat changed |
| `mentat` | builds, deploys and smoke-tests the Mentat service | `test`, `mentat-test`, `changes`, `gate` | gate ready, tests green, Mentat changed |

"Mentat changed" = a file under `mentat/`, `.github/workflows/` (the deploy flags and `SIGMA_GROUND_REF` live there) or `.dockerignore`
differs from the last successful deploy; or the run is manual; or there is no earlier green deploy, or the comparison fails.
**The portal never `needs` a Mentat job or `changes`**, so a wrong answer there can never hold up or skip the portal. A manual run
("Run workflow") redeploys Mentat without touching it (e.g. after bootstrap creates its identity, which the `mentat` job skips with a
notice until then).

| Push | `test` | `portal-image` | `portal` | `infra` | `changes` / `mentat-test` / `mentat` |
|---|---|---|---|---|---|
| normal (portal, tools, ...) | runs | runs | after test + image | after test | `changes` runs; mentat jobs skipped |
| docs only | runs | runs | runs | runs | mentat jobs skipped |
| touches `mentat/**` or `.github/workflows/**` | runs | runs | runs | runs | all run |
| manual run | runs | runs | runs | runs | all run |
| a test fails | red | may finish | skipped | skipped | mentat skipped (needs `test`) |
| gate not ready (bootstrap pending) | runs | skipped | skipped | skipped | mentat skipped |

A failed test stops every deploy. Claude reads the job logs and fixes forward: you don't need to.

### Expected timing

Measured on GitHub before this change (median of 8 push deploys): **242 s** from push to deploy finished; the `test` job (102-122 s)
and then the `portal` job (93-105 s: `setup-gcloud` 23-30 s, build + push 34-45 s, deploy 25 s) were the critical path.

| Stage | Before | Expected now |
|---|---|---|
| tests (critical path) | 102-122 s, one serial job | about 50-70 s: pip cached, pytest on 2 workers, flask-api in a parallel job |
| image build + push | 34-45 s after the tests, behind 23-30 s of `setup-gcloud` | inside the test window (about 40-60 s, warm cache) |
| deploy to Cloud Run | 25 s | 25 s plus about 5 s of setup (the new revision serves when this step ends) |
| push to live | **242 s** | about 100-130 s |

Estimates, not measurements: the first run after this change builds the Docker cache cold, and pytest on a 2-vCPU runner can't be more
than about 2x faster. `make loop-time` (see "Timing the loop") shows the real numbers.

## Rolling back the portal (from a phone)

Before it deploys, the `portal` job notes which Cloud Run revision is serving. If the deploy or its smoke test fails (the smoke test
also checks `/home/workshop` answers 401 without a token, `/privacy` answers 200 and `/me` signed out never answers 5xx), the job moves
ALL traffic back to that revision and ends red with an error saying it was rolled back. A deploy that passes but is wrong in a way
only you see is undone by hand: Actions > **rollback** > Run workflow, box blank
([`rollback.yml`](../.github/workflows/rollback.yml): goes back one revision, lists the last 5 with their commits; `latest` undoes it).
A rollback pins traffic to one revision, so every deploy ends by sending traffic to the newest revision again. The whole runbook,
phone-first, including what only the PC can fix: [portal/remote-recovery.md](portal/remote-recovery.md).

## Changing game servers

| You say | What happens |
|---|---|
| "Change the Valheim world name / password" | Admin → Settings, then **Restart & update** — no deploy needed |
| "Start Valheim over from a seed" | Admin → Settings → **World seed** (blank = `skippyhasyourmoney`), then **Restart & update**. At boot a world with a different seed is set aside on the disk (`replaced-worlds/`, never deleted) and a new one is generated from the seed. `keep` leaves the world alone |
| "Roll a game back after a bad day" | `ops` workflow: `backups <game>` lists the rollback points, `restore-game <game> <archive or latest>` puts one back (the current files are set aside, not deleted) |
| "Update the servers / mods" | Admin → **Restart & update** (every boot re-pulls images and game updates) |
| "Add a game / change ports / change the compose file" | Claude edits `games/` + `infra/gcp-games/`, pushes; `infra` applies; the change lands at the VM's next boot (Restart) |
| "Change the portal" | Claude edits `portal/`, pushes; live in ~3 minutes |


## Cost alarm (monthly budget)

[`infra/gcp-games/budget.tf`](../infra/gcp-games/budget.tf) creates a billing budget on the project (default
$30 a month, `budget_monthly_usd`) that emails at 50%, 90% and 100% of it. It exists only when a billing account
id is supplied, so until then a push changes nothing and needs no billing permission. To switch it on:

1. **The account id** (`XXXXXX-XXXXXX-XXXXXX`): console → Billing, or `gcloud billing accounts list`. The Captain
   has to supply it; nothing in the repo knows it.
2. **Give it to the pipeline** as the repository variable `BILLING_ACCOUNT` (GitHub → Settings → Secrets and
   variables → Actions → Variables). `deploy.yml` passes it to Terraform as `TF_VAR_billing_account`. (Applying by
   hand: `billing_account = "..."` in `terraform.tfvars`.) It is not a secret.
3. **Let the deployer manage budgets on that account**: Billing → Account management → Add principal →
   `skippy-deployer@skippy-tel.iam.gserviceaccount.com`, role **Billing Account Costs Manager**
   (`roles/billing.costsManager`, which holds `billing.budgets.*`). It is granted on the billing account, not the
   project, so this repo's Terraform can't do it. The role name is from Google's documentation and has not been
   tried here: if the `infra` job fails with a permission error on `billing.budgets.create`, this step is what's
   missing.
4. **Push.** The `infra` job enables `billingbudgets.googleapis.com` (and `monitoring.googleapis.com` if you set
   `budget_alert_email`) and creates the budget.

Emails go to the billing account's administrators and users, which is the budget's default. `budget_alert_email`
adds one more address through a Cloud Monitoring email channel. Untested against a live billing account: nobody
here has one to apply it to yet, so expect to read the first `infra` log after switching it on.

The portal's Watcher (Dashboard) warns separately, and sooner: when the games VM has been on for longer than the
watchdog's `max-hours` limit plus an hour, or for over 2 hours with nobody playing (see
[docs/games/README.md](games/README.md#auto-sleep-the-session-limit-and-how-to-see-why-a-vm-stayed-up)).

## Remote operations (`ops` workflow)

`.github/workflows/ops.yml` is a manual workflow for operating the games VM
without the portal: `status`, `logs [game]`, `start <games>`, `stop`,
`restart`, plus the on-VM commands (`tail`, `search`, `stats`, `restart-game`, `backups`, `restore-game`). It runs `scripts/remote.py` (the portal's own `gcp.py` / `ops.py` /
`diagnostics.py`) as the deployer identity, and masks every secret value in
the job log. It exists so Claude can diagnose and act on the server itself. `logs` (no game) includes the
idle watchdog's evidence block: why the VM does or doesn't go to sleep.

## Timing the loop

The loop has one stopwatch: **from "prompt sent" to "the new version is visible"**. [`tools/loop_timer.py`](../tools/loop_timer.py)
reads it off skippy-core's own records (since 2026-10-25 the loop doesn't touch GitHub: docs/no-github.md) and off the portal's
`/version`; a stage it has no record for prints `n/a (reason)`, never a guess. Standard library plus `ssh` and `git`, so it runs from Git
Bash on Windows and on Linux.

```bash
python tools/loop_timer.py --watch --since now             # start BEFORE the push: waits for the push, CI, the deploy and /version to flip
python tools/loop_timer.py --since "12 minutes ago"        # after the fact (the exact moment of "visible" is then unknowable)
python tools/loop_timer.py --sha 8adcd7e --json --utc      # one commit, as JSON, in UTC
make loop-watch SINCE=now                                  # the same through make (loop-time for after the fact; LOOP_ARGS="...")
```

Flags: `--since` (an ISO time, `N minutes ago`, `now`), `--sha`, `--watch` (Ctrl-C prints what was seen so far), `--portal URL`
(default production), `--core HOST` (default `skippy-core`), `--house PATH` (the bare repo, default `D:/trunk/git/skippy-tel.git`, or
`LOOP_HOUSE_GIT`), `--bridge [URL]` (see the last section), `--json`, `--utc`. Without `--sha` or `--since` it times the newest commit CI
has seen. Exit status: 0 = printed and live (or nothing failed), 1 = CI or the deploy failed, or the version never showed up while
watching, 2 = couldn't run (no such commit, skippy-core unreachable).

Where each time comes from (all read only: one `ssh skippy-core python3 -` per look, every file world-readable):

| Record | What it gives |
|---|---|
| the house repo's reflog (`D:\trunk\git\skippy-tel.git`, `core.logAllRefUpdates always`, switched on 2026-10-27) | **the push**: when main moved to (or past) the commit. Without an entry: the ref file's time while it is still main's tip, else the commit date, and a note says which. While watching, the moment this machine saw main move |
| CI, `/var/lib/skippy-core/ci/skippy-tel/results/<sha>.json` (`core/ci/ci.py`) | `at` (CI took it up), `finished_at`, and each job's `started_at` / `finished_at` (epoch seconds) |
| the portal deploy, `/var/lib/skippy-core/cd/state.json` runs (`core/cd/cd.py`) | the run's `created_at` / `updated_at`; each job's `started_at` / `completed_at`; the portal job's **`serving_at`**: all traffic on the new revision |
| Core's deployer, `/var/lib/skippy-core/deployer/status.json` (`core/deployer/deployer.py`) | `last_good.started` / `last_good.at`, only while the last good deploy is this commit (it keeps no history) |
| the portal's `/version` | **visible**: the first second this machine saw it report the commit (polled every second while watching) |

The per-job stamps, `finished_at` and `serving_at` were added on 2026-10-27. An older record still prints: a CI job shows only how long it
took, and the end of the deploy run stands in for `serving_at` (a little late, and the note says so).

### Reading the table

A real loop (2026-10-27, commit 699788e, read afterwards, in UTC; its records predate the per-job stamps):

```
stage                               start     end          took  note
prompt -> push                                                   n/a (no --since: pass --since 'N minutes ago' ...)
wait for CI (timer, 1 min)          08:13:36  08:14:17      42s
CI (skippy-core)                    08:14:17  08:15:09      52s
  suite                                                     52s  no start/end stamps in this record, only how long it took
wait for the deployer (timer)       08:15:09  08:16:08      58s
deploy run 35 (cd.py)               08:16:08  08:17:23    1m15s
  build portal image                                             n/a (no stamps in this record (success))
  deploy portal                                                  n/a (no stamps in this record (success))
Core services (deployer)                                         n/a (the deployer keeps only its last good deploy, ...)
visible on the portal                                            n/a (<portal>/version reports 79d3678, not 699788e: ...)
TOTAL push (no --since) -> serving  08:13:36  08:17:23    3m47s  visible was not observed, so this stops where ...
critical path: push -> CI 42s -> CI 52s -> CI -> deploy run 58s -> deploy run to serving 1m15s   [push -> serving: 3m47s]
```

| Row | What the two times are |
|---|---|
| `prompt -> push` | `--since` (when the prompt was sent) to the push. `n/a` without `--since`. With `--bridge` marks it splits further |
| `wait for CI (timer, 1 min)` | the push to CI taking the commit up: CI's timer ticks every minute, and it waits while the private Skippy works |
| `CI (skippy-core)` and its jobs | CI's start and end, and each job's own; the jobs run **side by side** in their own containers, so they overlap |
| `wait for the deployer (timer)` | CI's end to cd.py creating its run (cd.py's timer ticks every minute) |
| `deploy run N (cd.py)` and its jobs | the run, then `build portal image`, `deploy portal` (its note says when all traffic moved), `mentat deploy` and `infra` when they changed, one after another |
| `Core services (deployer)` | Core's own services, deployed beside the portal (its timer ticks every 2 minutes): off the portal's critical path |
| `visible on the portal` | from `serving_at` to the first second this machine saw `/version` report the commit. A **negative lag** means traffic switched a moment before gcloud returned |
| `TOTAL` | the loop start (`--since`, else the push) to `visible`; if `visible` wasn't observed it stops at serving and says so |
| critical path | the stages are one after another now: push -> CI -> the deployer's wait -> run start -> image -> deploy to serving -> visible. `push -> serving` is the headline number |

A `visible` that shows `n/a (already live ...)` means the new commit was already serving at the timer's first look, so when it appeared
can't be known (start `--watch` before the push). Same-commit redeploys wait for a *new revision* of that commit instead.
Times are UTC in the arithmetic and local in the table (`--utc` for UTC); the table is ASCII so a Windows console prints it as it is.

### `/version` and the footer stamp

The portal image carries `GIT_SHA` and `BUILD_TIME` (baked in at build, so a rolled-back revision reports its own build); Cloud Run sets
`K_REVISION`. `GET /version` (public, `Cache-Control: no-store`, no secrets, [`portal/buildinfo.py`](../portal/buildinfo.py)) answers
`{commit, short, built_at, revision, started_at}`: `dev` / empty outside the image. Signed-in pages show it as a small muted line in the
footer, `build 8adcd7e · 12:03` (the build time in the viewer's own clock; full commit and revision on hover): that is how the Captain sees
which build he is looking at. The login page and the public pages never show it.

### What the speed-ups should do

(GitHub Actions days, kept for the record: the loop runs on skippy-core now.) Measured before (the last eight successful push deploys, no queueing): push to deploy-finished **242 s**, median. The critical path was gate (3 s) ->
`test` (102-122 s: pip 10-16 s, pytest 79-85 s) -> `portal` (93-105 s: setup-gcloud 23-30 s, image build + push 34-45 s, Cloud Run deploy 25 s,
smoke). The build is not on the critical path any more once it runs next to the tests, pip comes from a cache, and pytest runs on both
cores; the image also stops waiting for the tests. Expected, not yet measured: tests ~60-70 s, the `portal` job ~55-60 s (about 30 s if
setup-gcloud can be skipped), so **push -> serving about 2 min** instead of 3m10s. Only `make loop-watch` on real pushes proves it: compare
the `push -> serving` figure and the critical path in the table before and after, and keep the JSON of each run (`--json`).

### The pre-push check

`python tools/affected_tests.py` (also `make test-affected`) runs only the tests a change can break, so the agent's own check before a push
takes seconds instead of the ~4 minutes the whole suite takes serially on skippy-pc. CI stays the full gate. A file inside a test folder runs
that folder; `portal/`, `memory/`, `mentat/`, `tools/` and `services/<name>/` run their own tests (flask-api in its own session: different
requirements); any test that *names* the file (its file name next to its folder) is added, which is how a doc, a shell script or a module a
test loads by path reaches the tests that read it; docs nothing names run nothing. **Cross-cutting changes get the full suite (the two CI
commands)**: any `requirements*.txt`, `conftest.py`, `.github/**`, a Dockerfile or compose file, `pytest.ini`/`pyproject.toml`,
`portal/catalog.py`, a file nothing knows, or a base it can't find. Changed `.py` files are compiled and changed `.sh` files get `bash -n`.
With `pytest-xdist` installed it uses `-n auto --dist loadfile` (one test file stays on one worker); without it, plain pytest. `--list`
shows the plan, `--files a b` names the change, `--full` forces everything, `--base REF` compares with another ref.

### What still has no timestamps

`prompt -> push` is one row because the agent's side doesn't stamp itself yet. `--bridge` reads what the Claude bridge can tell: the run's
age (so `bridge received`) now, and `first edit` / `git push` once the bridge's events carry a `ts` (needs `SKIPPY_HOME_TOKEN` in the shell);
with those marks the row splits into `prompt -> bridge received -> first edit -> git push -> push`. Not measurable yet: the portal's own
"send" moment (portal send -> bridge start), the time spent editing versus testing, and the local test run before the push. A later change
adds those stamps; the timer already tolerates their absence.
